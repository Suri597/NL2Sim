# NL2Sim — Natural Language (and Sketch) to Supply Chain Simulation

NL2Sim is an end-to-end pipeline that converts a supply chain scenario —
described in plain English, drawn as a sketch, or both — into a validated
simulation configuration and runs a discrete-event simulation to produce
KPI results. No coding or JSON writing required.

---

## What it does

```
Text description  and/or  hand-drawn / photographed sketch
        ↓
Config generation
    text  → LLM (OpenAI fine-tuned model) produces structured JSON
    graph → schema-aware extraction + clarification dialogue
    both  → generated independently, then reconciled (node matching,
            facility typing, edge resolution, material detection)
        ↓
Multi-layer validation + interactive, LLM-phrased repair
        ↓
Interactive graph review (auto-opens in your browser)
        ↓
Reliability scoring (text-only runs; skipped automatically otherwise)
        ↓
Discrete-event simulation (SimPy)
        ↓
KPI results + what-if analysis
```

---

## Key features

- **Three input modes** — text only, graph only (sketch/photo), or both
  together, reconciled against each other
- **NL → JSON** — fine-tuned GPT model translates plain English to a fully
  structured supply chain config
- **Graph → JSON** — a hand-drawn or photographed sketch is turned into a
  config directly, with the model asking clarification questions only
  where it's genuinely unsure, never inventing values
- **LLM-phrased repair conversation** — every question asked during repair
  is generated by an LLM from the schema, the entity's known context, and
  your original description, not a fixed template
- **3-layer validation** — structural, cross-reference, and
  simulation-readiness checks with interactive, guided repair
- **Reliability scoring** — quantifies how well the generated JSON matches
  the original description (text-only runs)
- **DES simulation** — SimPy-based engine supporting periodic supply,
  inventory threshold, demand-driven procurement, backorder and lost sales
  policies, resource failures, batching
- **What-if analysis** — modify any parameter in plain English and
  re-simulate; each what-if variant gets its own version number
- **Resume-safe pipeline** — `--from-config` flag lets you skip straight to
  validation from a saved config

## Prerequisites

- Python 3.9+
- **OpenAI API key** (default backend — see below)
- Optionally, an **Azure OpenAI API key + endpoint** (Azure is supported as
  an alternate backend in the code, but is no longer selected via an

## Installation

**1. Clone the repository**

```bash
git clone https://github.com/Suri597/NL2Sim.git
cd NL2Sim
```

**2. Create a virtual environment**

```bash
python -m venv .venv
source .venv/bin/activate        # macOS / Linux
.venv\Scripts\activate           # Windows
```

**3. Install dependencies**

```bash
pip install -r requirements.txt
```

The graph_output/graph_input merge added `networkx`, `pyvis`,
`opencv-python`, `openai`, and `python-dotenv` on top of the original
dependency list. If your `.venv` is pinned to an older Python (this project
has been run against 3.9.12), some of these may need older pins than the
latest available on PyPI — install without a version pin and let pip
resolve a compatible version, then update `requirements.txt` accordingly.

**4. Set up environment variables**

```bash
cp .env.example .env
```

```env
# ── OpenAI (default backend) ───────────────────────────────
OPENAI_API_KEY=sk-...your-key-here...
OPENAI_MODEL=ft:gpt-4.1-...your-finetuned-model-here...

# ── Azure OpenAI (alternate backend, not selected via menu) ─

AZURE_OPENAI_API_VERSION=2024-10-21
AZURE_BASE_MODEL=gpt-4.1
```

## Quick start

```bash
cd scripts
python run_pipeline.py
```

You'll be prompted to:
1. **Choose how to provide the scenario** — Text only / Graph only / Graph + Text
2. If a graph is involved: capture live via webcam, or point to an existing image
3. If text is involved: type a description or load it from a `.txt` file
4. Choose whether to include system instructions (more accurate, more tokens)
5. Work through validation/repair — every question is phrased for you in
   plain language, grounded in your scenario
6. Review the auto-opened interactive graph; proceed, retry, or abort
7. If text-only: choose whether to compute the reliability score, or skip it
8. View simulation results
9. Optionally run what-if analyses

---

## Input modes

- **Text only** — same as the original pipeline: type or load a description,
  the fine-tuned model produces the config directly.
- **Graph only** — no description exists to fill in attribute data, so
  `graph_only_to_json.py` uses a schema-aware prompt to extract everything
  legible from the image (materials, entities, connections) and generates
  targeted clarification questions for anything genuinely ambiguous. It
  never invents a value it isn't confident about — if it can't tell, it
  asks.
- **Graph + Text** — both sources are generated independently, then
  `merge.py` reconciles them in stages: node names are matched (exact
  match → fuzzy match → an LLM-mediated dispute round for anything left
  over), facility types are classified, edge existence is confirmed
  through an interactive dialogue, and material types/names are filled in
  deterministically from what's already known.

The original interactive "OpenAI or Azure?" menu has been removed —

## The repair conversation is LLM-framed

Every question the repair step asks — "how long does this supplier take to
deliver?", "which of these should this edge actually connect?" — is
generated by an LLM (`llm_humanize.py`), not pulled from a fixed template.
Each question is built from:

- the schema's field meanings,
- whatever's already known about the entity being asked about,
- your original description (or a note that this run came from a sketch
  with no description),
- and, for multi-option repair menus (delete vs. retarget vs. sync, change
  facility type vs. add material, etc.), the actual situation being
  resolved — so the question matches the real decision rather than reading
  the raw field name literally.

Answers are cached per (field shape, entity, situation) within a run so the
same kind of question isn't regenerated needlessly. If the API call fails
for any reason, a plain-text fallback is shown instead of the run stalling.

---

## Config versioning

`config_info.version` is never asked from the user. A fresh run is always
assigned `1.0` automatically; each what-if iteration bumps it (`1.1`,
`1.2`, ...), so the version string on a saved config tells you exactly how
many what-if steps produced it.

---

## Reliability scoring

The reliability score measures how closely the generated config matches a
natural-language description — that comparison isn't meaningful when a
graph/sketch was part of the source (there may be no description, or it
never fully specified the topology on its own). So:

- **Graph-only or Graph+Text runs** — scoring is skipped automatically,
  with an on-screen note explaining why.
- **Text-only runs** — you're asked whether to compute it or skip straight
  to simulation.

---

## A note on `Instant` distributions

Several time-based fields offer "Instant (always exactly 0)" as a shortcut
during repair. For one-shot delays (supplier lead time, transfer time,
payment lead time) this is safe. For fields that generate a **recurring**
event stream — `customer.arrival_time`, `facility.operation.operation_cycle`,
`resource.service_time`, `resource.failure.uptime`/`downtime` — `Instant`
effectively means "infinitely often," which can spin the discrete-event
engine in a zero-time loop that never advances the simulation clock. The
repair prompt no longer offers `Instant` for these five fields; a real
distribution must be chosen instead.

---

## Things NL2Sim does not model

- **Reverse logistics / returns.** If a description mentions a returns or
  repair facility, the correct resolution during repair is to delete that
  facility entirely — there is no valid way to route it through the
  forward-only supplier → facility → customer schema this tool assumes.

## Example description

```
A CPU manufacturer sources microprocessors from Process Go., who delivers
with a constant 7-day lead time and charges $200 per unit. Payment is due
30 days after delivery. Microprocessors arrive daily in batches uniformly
distributed between 60,000 and 80,000 units. Memory chips are supplied by
Memory Star with a lead time uniformly between 10 and 18 days, at $100 per
unit, delivered every 14 days in batches of 1,960,000 units.

Assembly takes place at the Fab facility. Each CPU requires 1 microprocessor
and 2 memory chips. One production cycle takes 1 day. Finished CPUs are
transferred immediately to a Warehouse. Initial CPU inventory is 3,000,000
units.

Ross Associates orders CPUs every 30 days. Demand is uniformly distributed
between 1,800,000 and 2,200,000 units. Deliveries take 14 days. If inventory
cannot fully satisfy an order, available stock is shipped and the rest is lost.
CPUs are sold at $500 per unit with 30-day payment terms.

The simulation runs for 365 days with 10 replications.
```

## Simulation engine

The simulation engine (`simulate.py`) supports:

| Feature | Details |
|---|---|
| Procurement schemes | `periodic_supply`, `inventory_threshold`, `demand_driven` |
| Shortage policies | `backorder`, `salelost`, `backorder_partial`, `salelost_partial` |
| Resources | capacity, service time, batching, failure/repair |
| Multi-product | multiple products with different BOMs |
| Intermediate materials | multi-stage production |
| Financial KPIs | revenue, procurement cost, holding cost, shortage cost, profit, cash balance |
| Service KPIs | fill rate, units delivered, units lost, backorder |
| Inventory KPIs | average and ending inventory per material |
| Time-series data | per-replication financial, service, and daily inventory series saved to `results/` |
| Missing fields | `"missing"` placeholders and absent fields handled automatically via `normalize_config()` |

---

## JSON schema

The full schema supports the following sections:

```
config_info            → scenario name and version (auto-assigned; see Config versioning)
raw_materials           → input materials (names)
intermediate_materials  → semi-finished goods with BOM
products                → finished products with BOM
inventory               → procurement scheme, costs, initial stock
supplier                → lead time, cost, capacity, payment terms
resource                → machines with service time, batching, failure
facility                → manufacturing or warehouse, operations
customer                → demand, arrival time, shortage policy, pricing
nodes                   → supply chain graph nodes
edges                   → material flows with transfer times
simulation              → horizon, replications, warm-up, time unit
```

Full schema example is in `scripts/schema.py`.

---

## Encoding conventions

| Value | Meaning |
|---|---|
| `supplier_capacity` absent/`"missing"` | Unlimited capacity (`inf`) |
| `batch_size = -1` | Flush all available inputs every operation cycle |
| `review_time` absent/`"missing"` | Defaults to 1 time unit |
| `transfer_time` absent/`"missing"` | Immediate transfer (0 delay) |
| `warm_up` absent/`"missing"` | Defaults to 0 |
| `random_seed` absent/`"missing"` | Defaults to 12345 |
| `"missing"` | Field not provided by the source — repair will prompt |

---

## Validation layers

**Layer 1 — Field presence / type / enum**
Checks required fields are present and not left as `"missing"`, that
values match their expected type, and that enum-constrained fields
(distribution type, material type, facility type, shortage policy, time
unit, etc.) hold a recognized value.

**Layer 2 — Cross-reference consistency**
Checks BOMs reference known materials, edges reference real nodes,
inventory entries exist for every declared material, facility
`inventory_managed`/`operation.input` stay consistent with what edges
actually deliver, and catches duplicate names/edges and name collisions
across sections.

**Layer 3 — Structural feasibility**
Checks every raw material has a supplier and is consumed somewhere, every
product is producible and has a customer, every facility has both an
inbound and outbound edge, every product has an end-to-end path from
supplier to customer, and flags a simulation horizon that's implausibly
short relative to the supply chain's own cycle time.

If any layer finds issues, `repair_orchestrator.py`'s verify → repair →
re-verify loop resolves what it can automatically (e.g. defaulting
`transfer_time` to instant, auto-correcting a plural/singular enum typo)
and interactively prompts for the rest — every prompt phrased in plain
language via `llm_humanize.py` (see above), not a raw field path.

## Fine-tuning on Azure OpenAI

Scripts in `finetune/` handle uploading training data and launching
fine-tuning jobs on Azure OpenAI / Microsoft Foundry.

**Upload training data**

```bash
cd finetune
# Fill in credentials and TRAINING_FILE_NAME in upload_file.py, then:
python upload_file.py
```

**Start a fine-tuning job**

```bash
# Using an already-uploaded file ID
python finetune_job.py --training-file file-abc123

# Upload and fine-tune in one step
python finetune_job.py --upload ../outputs/data_gen/dataset/train.jsonl

# With validation file and custom hyperparameters
python finetune_job.py \
    --training-file file-abc123 \
    --validation-file file-xyz789 \
    --epochs 3 \
    --batch-size 4 \
    --lr-multiplier 0.2
```

Once fine-tuning completes, add the deployment name to `.env`:

```env
AZURE_FINETUNED_MODEL=your-finetuned-deployment-name
```

## Troubleshooting

**`OPENAI_API_KEY is not set`**
Make sure your `.env` file exists in the root directory and contains your
API key.

**`OPENAI_MODEL is not set`**
Set `OPENAI_MODEL` in your `.env` file to your fine-tuned model string
(e.g. `ft:gpt-4.1-2025-04-14:personal:nl2sim-ft:Dkz8vnRw`).

**`AZURE_OPENAI_API_KEY is not set`**
Only relevant if you're using Azure directly (see
[Model backend](#model-backend)) — make sure `AZURE_OPENAI_API_KEY` and
`AZURE_OPENAI_ENDPOINT` are set in your `.env` file.

**`DeploymentNotFound` on Azure**
The model name in `AZURE_BASE_MODEL` or `AZURE_FINETUNED_MODEL` must match
the exact deployment name in your Azure resource, not the model name.
Check **Models + endpoints** in Microsoft Foundry.

**`ModuleNotFoundError`**
Make sure you are running from inside the `scripts/` directory and your
virtual environment is activated.

**A package version conflict during `pip install`**
If your `.venv` is on an older Python (e.g. 3.9), some newer packages
(especially `networkx`) may not have a compatible release. Install without
a version pin (`pip install networkx`) and let pip resolve a compatible
version, then update `requirements.txt` to match.

**Reliability score fails with a quota error**
The pipeline will ask if you want to skip the score and continue to
simulation — choose the skip option. Note that for graph-derived runs,
scoring is skipped automatically regardless (see
[Reliability scoring](#reliability-scoring)).

**Validation errors after generation**
The repair loop will guide you through fixing them one by one, with every
question phrased in plain language and grounded in your scenario. If a
question ever feels mismatched to what's actually being asked, that's
worth reporting — it usually means the LLM-framing system needs a nudge
for that specific field shape.

**Simulation seems to hang / never finishes**
Check whether a recurring-event field (`customer.arrival_time`,
`operation_cycle`, `resource.service_time`, resource failure uptime/downtime)
was set to a zero-delay distribution — this can spin the simulation clock
without advancing. The repair prompt no longer offers "Instant" for these
fields specifically to prevent this; if you're editing a config by hand,
avoid it there too.

**A description mentions returns, repairs, or reverse logistics**
NL2Sim doesn't model reverse flows. When repair asks what to do with a
facility that has no valid outbound destination and the facility handles
returns, choose to delete it entirely — that's the schema-correct
resolution, not a workaround.
